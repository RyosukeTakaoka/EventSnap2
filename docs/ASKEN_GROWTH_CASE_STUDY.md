# あすけん — 成長事例からの構造抽出と EventSnap への応用

累計1,400万人・MAU151万人のヘルスケアアプリ「あすけん」の成長メカニズムを調べ、
EventSnap（イベント専用の写真共有アプリ）に何が使えて何が使えないかを整理する。

参考：姉妹プロジェクト Rotash にも同じ出発点の資料 [`docs/ASKEN_GROWTH_CASE_STUDY.md`](https://github.com/RyosukeTakaoka/Rotash/blob/main/docs/ASKEN_GROWTH_CASE_STUDY.md)
があり、判定基準や語彙（MUST/SHOULD/LATER/DON'T）はそちらと揃えている。
ただし EventSnap と Rotash は前提がまったく違うため、結論は別々に出す：

| | あすけん | Rotash | EventSnap |
|---|---|---|---|
| 利用単位 | 個人（毎日） | 固定7人グループ（週次） | **イベントごとの一時的な集まり**（人数上限なし・数時間〜数日） |
| 反復の性質 | 同じ人が毎日戻る | 同じ7人が毎週戻る | **毎回メンバーが変わりうる**（文化祭の代替わり、旅行のメンバー変更等） |
| 継続の主体 | 個人の習慣 | グループの習慣 | **イベント主催者・団体の習慣**（次のイベントでまた使うか） |

この違いが、後述する結論（特に §5）を大きく左右する。

## 0. 現状の事実（コードを読んだ上での整理）

Rotash の `GROWTH_DIAGNOSIS.md` の作法にならい、**推測ではなく実装から分かることだけ**を先に書く。

| 項目 | 内容 | 出典 |
|---|---|---|
| 参加導線 | QRコード読み取り（アプリ内蔵スキャナ） + Universal Link + **App Clip**（未インストールでも閲覧可能） | README |
| 招待の性質 | Rotashの「未完成の作品を見せる招待」に近いことを**既に実装済み**。App Clipはその場の写真・Event Reel風プレビューを未インストールのまま見せ、フルアプリDLに繋げる設計 | README, `EventSnapClip/` |
| 記録の摩擦 | 撮影と同時に全員のアルバムへ自動追加。**投稿ボタンが無い**（あすけんの「低摩擦記録」と同じ方向の設計） | README |
| 共有物のブランド化 | `SocialCardService` が写真主役のテンプレート（Editorial/Bold/Minimal）でシェア画像を生成。Vision解析で安全ゾーンを算出しタイポグラフィを重ねる | `Services/SocialCardService.swift` |
| 段階的な共有物生成 | `ShareCollageBuilder` がイベント中に写真が数枚たまるたびEvent Reelを自動生成（終了を待たない） | `Services/ShareCollageBuilder.swift` |
| 通知 | ローカル通知のみ。タイムカプセル公開時、リアクション時、イベント再開時 | `Services/NotificationService.swift`, git log |
| 複数イベント対応 | `EventSwitcherView` で開催中/終了済みイベントを切り替え可能。**過去イベントは端末に履歴として残る**が、現状はフラットなリスト | `Views/Components/EventSwitcherView.swift` |
| 初回体験 | 実UIをスポットライトで示すインタラクティブチュートリアルあり | `Services/OnboardingTutorialManager.swift` |
| 分析・計測 | **1行も無い**（`grep` 結果ゼロ） | 全文検索 |
| 課金・マネタイズ | **無い**（StoreKit関連コードなし） | 全文検索 |
| 法人・団体向け導線 | **無い**（学校・結婚式場・サークル等に向けた専用フローは存在しない） | 全文検索・README |

**ここから読めること：** EventSnap は、Rotash が `GROWTH_STRATEGY.md` の MUST（M1〜M3 相当）として
これから実装しようとしていたもの——**招待がそのまま作品プレビューになること、通知、ブランド化された
共有物**——を**既に実装済み**の状態にある。Rotashより一歩進んだ位置にいる。
弱いのは「計測」と「個人利用を超えた配布経路」の2点である。

## 1. AI栄養士キャラクター「みきちゃん」— EventSnapでの当てはめ方

あすけんは記録するたびAI栄養士キャラクター「みきちゃん」が人格を持った声でフィードバックを返す。
[（出典）](https://news.mynavi.jp/article/20210914-1971945/)
これが「今日は何て言われるかな」という**個人単位の期待**を毎日作っている。

### EventSnapへの示唆：個人向けではなく「場の空気」向けに使える

EventSnapは個人が毎日開くアプリではなく、**イベントという短い期間に集中して開くアプリ**である。
だから「みきちゃん」のような**個人への語りかけキャラクター**をそのまま移植する理由はない
（Rotash版の判定と同じくDON'T）。

しかし1つだけ構造が近い場所がある。**Event Reel と タイムカプセルの公開演出**である。
現状 `ShareCollageBuilder` はテンプレート（Editorial/Bold/Minimal）で写真を並べるだけで、
「なぜこの写真が選ばれたか」を言葉にする要素が無い。

あすけんの学びを言い換えると：**データの提示に、短い一言の"人格"が乗ると情緒が動く。**
EventSnapで安全に使える形は、**個人キャラクターではなく「イベント全体を見ている視点」の一言**にする：

```
やらない：
  キャラクターを新設し、個々の写真に「いいね、その笑顔！」のようなコメントを付ける
  → 個人への評価になり、後述§2のリスク（相互評価・気まずさ）を生む

やってよい：
  Event Reel生成時、EventReelPhotoSelectorが「多様性」で選んだ根拠を
  1行の見出しとして添える（例：「この30分でいちばん動きがあった瞬間」）
  → 写真の"選ばれた理由"を言葉にするだけで、AI主語のまま個人を評価しない
```

**→ 判定：DON'T（個性を持つマスコット/キャラクターの新設）。**
**SHOULD（LATER寄り）：Event Reel見出しの自動生成文**は、既存の `EventReelPhotoSelector` の
選定ロジック（多様性・品質）をそのまま言語化するだけなので実装コストが小さく、検討の価値がある。

## 2. 点数化・ゲーミフィケーション — Rotashと同じ理由で警戒する

あすけんは食事に点数をつけて可視化する。個人向けだから安全に機能している。
[（出典）](https://note.com/jgamifa/n/n61c0d8b48ef5)

### EventSnapへの示唆：「イベントの盛り上がりスコア」は個人化しない限りで検討可

EventSnapにも「点数化したくなる場所」がある。**イベント全体の盛り上がり**（写真枚数・リアクション数）を
Live Activity やウィジェットに可視化するアイデアである。これは Rotash の Memories 積層（C-2）と
似た発想——**数字ではなく雰囲気で継続・熱量を伝える**——として検討の余地がある。

ただし、あすけんの点数化がそのまま危険な形に転びうる境界線がある：

```
やってはいけない：
  「◯◯さんの投稿数ランキング」「今日いちばん撮った人」
  → 個人の貢献度比較になる。Rotashが J-1 #2 で禁じた「サボり検知」と同じ構造。
    参加者の間に気まずさが生まれ、「その場にいる全員で完結する」という
    EventSnapの前提（招待コードのような経路をあえて用意しない、README冒頭の思想）と矛盾する

やってよい：
  イベント全体の熱量を1つの数字・visualにする（個人に紐付けない）
  例：Live Activityに「この1時間で12枚」のような**集合の勢い**だけを出す
```

**→ 判定：個人単位の点数化・ランキングは DON'T。イベント全体の集合値の可視化は LATER（要検討）。**
Rotashが点数化を個人向け機能として却下した理由が、ここでも同じ形で当てはまる。

## 3. プッシュ通知の作法とセグメント設計

あすけんは対象を3セグメント（未登録／未記録／定期記録者）に分けて通知し、
初回記録率+8pt・新規7日後リテンション+4ptを達成した。
成功要因は**キャラクター名を使うこと・悲しい表情の絵文字**、失敗要因は**煽り文言**だった。
[（出典）](https://marketing.sendai.garden/%E3%83%AA%E3%83%86%E3%83%B3%E3%82%B7%E3%83%A7%E3%83%B3%E7%8E%877%E3%83%9D%E3%82%A4%E3%83%B3%E3%83%88%E6%94%B9%E5%96%84%EF%BC%81%E3%80%8E%E3%81%82%E3%81%99%E3%81%91%E3%82%93%E3%80%8F%E3%81%AE%E3%82%A2/)

### EventSnapへの示唆：イベント内でも同じ3セグメントが存在する

現状の通知（タイムカプセル公開・リアクション・再開）は「既に撮っている・参加している人」向けである。
あすけんの3セグメントをEventSnapの1イベント内に当てはめると：

| あすけんのセグメント | EventSnapでの対応 | 現状 |
|---|---|---|
| ①会員登録未完了 | QR/App Clipでイベントを見たが、まだ参加（フルアプリDL）していない人 | 通知の送りようがない（未インストールのため） |
| ②1回も記録なし | **参加したが1枚も撮っていない参加者** | **通知なし** |
| ③定期記録者 | 撮影・リアクションしている参加者 | 実装済み |

**②が空白である。** イベント開始から一定時間、写真を1枚も撮っていない参加者にだけ、
1回限りで「まだ0枚だよ、撮ってみて」ではなく——あすけんの学び（煽り文言は逆効果）に従い——
**Rotashの D-3 と同じ「作品の状態を淡々と伝える」文体**（例：「このイベント、もう32枚集まってるよ」）
で気づきを促す余地がある。

**→ 判定：SHOULD。** ただし押しつけがましくならないよう、**イベント中1回・煽らない文面**に限定する。
実装コストは小さい（`NotificationService` の既存のローカル通知予約の仕組みをそのまま使える）。

## 4. お友達紹介機能・招待導線 — EventSnapは既にあすけんより進んでいる

あすけんは2020年に後付けで友達紹介機能を追加した。
[（出典）](https://www.asken.inc/news/2020/12/28)
個人利用アプリは招待の理由が薄いため、インセンティブ付きの明示的な依頼が必要だった。

### EventSnapへの示唆：後付けの紹介施策は不要

EventSnapは**招待自体がイベント参加の手段そのもの**（QRを読めば即参加）であり、
あすけんのような「後から追加する紹介キャンペーン」は不要である。
これはRotashが M1（招待リンク+未完成作品画像）としてこれから作ろうとしていたものに近く、
EventSnapは**App Clipによるプレビュー**という、Rotashにもあすけんにも無い形でさらに一歩進んでいる
（インストール前に中身が見える）。

**→ 判定：現状維持。新規の紹介施策は不要。**
唯一の改善余地は、**App Clipのプレビュー画面が「これ何？」を十分に伝えているか**の検証である
（`docs/APP_STORE_SCREENSHOTS.md` 等、既存のプロモーション資料と整合させる程度で十分）。

## 5. 機会 α：法人・団体配布チャネル — EventSnapが最も活かせる示唆

あすけんは健康保険組合・企業人事と契約し、**従業員へ一括配布**される「あすけんプラス」を持つ。
1つの契約が数千〜数万人への配布に変わる、効率の良い経路である。
[（出典1）](https://www.asken.jp/lp/corporation/)
[（出典2：学研健康保険組合の導入事例）](https://g-kenpo.or.jp/service/page-13428/asken/)

### Rotashとの決定的な違い：EventSnapには「7人上限」のような制約がない

Rotash向けの資料では、この配布モデルは「7人上限と相性が悪く、代表者経由で7人単位に
分割しないと使えない」という留保付きだった。**EventSnapにはこの制約が存在しない。**

EventSnapは1イベントの参加人数に上限を設けていない（README: 少人数イベント想定だが、
コード上の cap は無い）。さらに**「イベント」という単位そのものが、法人・団体の日常業務と1対1で対応する**：

| あすけんの契約主体 | EventSnapで直接対応する主体 |
|---|---|
| 健保組合・企業人事 | **学園祭実行委員会・大学のサークル連合**（毎年イベントを主催） |
| — | **結婚式場・ブライダルプランナー**（毎週末、複数の式を回す） |
| — | **修学旅行・卒業旅行を扱う旅行代理店/学校**（年に何度も同型のイベントを持つ） |
| — | **社内イベント・運動会を企画する企業の総務部** |

あすけんは「健康管理という日常業務」に自社を差し込んだ。**EventSnapは「イベント運営という
業務そのもの」にすでにぴったり重なるプロダクトである。** これはRotashよりもEventSnapの方が
この配布モデルへの適合度が高いことを意味する。

**具体的な意味：**

1つの結婚式場と提携すれば、その式場が毎週末開催する式それぞれが独立した1イベントとして
何の追加開発もなく成立する（Rotashのように7人単位に分割する必要がない）。
学園祭実行委員会1つと組めば、模擬店ごと・クラスごとの複数イベントが並行して立ち上がる。

**→ 判定：MUST級の検討事項として新規追加を提案（Rotashの§5がLATERなのに対し、
EventSnapではより優先度が高い）。** 具体的な最初の一歩：

1. 主催者向けの「まとめて発行」機能——1団体が複数のイベントQRを一括生成できる導線
   （現状 `EventRepository.createEvent` は1件ずつの想定）
2. 主催者向けの簡易ダッシュボード（このQRから何件イベントが立ち上がったか）——§6の計測と表裏一体
3. まずは無償の実験として、身近な学園祭実行委員・結婚式場1件との提携で検証する
   （あすけんも最初は個別の健保組合との実験から広げている）

ただし、Rotashの診断と同じ注意点を1つ引き継ぐ：**計測が無いまま団体へ広げると、
何が効いたか分からないまま終わる。** §6を先に着手すること。

## 6. 集計データPR・計測 — 今のEventSnapに最も欠けているもの

あすけんは「痩せた人の総減量数8,440トン」のような自社データをPR化している。
[（出典）](https://dengekionline.com/article/202406/8271)
これができるのは、**大前提として計測が存在するから**である。

### EventSnapへの示唆

現状 EventSnap には分析コードが1行も無い（§0）。あすけんのPR手法を真似る以前に、
**「1イベントあたり平均何人参加し、何枚撮られ、Event Reelが何回生成されたか」を
知る手段が無い。** これは Rotash の `GROWTH_DIAGNOSIS.md` が指摘した
「律速変数はループの部品が実装されていないことそのもの」と同じ状態である。

**→ 判定：SHOULD（§5の法人展開より先にやるべき）。**
CloudKitのレコード数を集計するだけの読み取り専用スクリプト
（Rotashの `tools/rotash-stats.py` 相当）は、アプリ本体を変更せずに今日から作れる。
これが無いと、§5の法人提携も「効果があったかどうか」を誰にも説明できない。

## 7. まとめ

| 節 | 判定 | 理由 |
|---|---|---|
| §1 AI栄養士キャラクター | **DON'T**（個人向けキャラ）/ **LATER**（Event Reel見出しの自動生成） | 個人語りかけはEventSnapの「その場の全員」思想と合わない |
| §2 点数化・ゲーミフィケーション | **DON'T**（個人ランキング）/ **LATER**（集合値の可視化のみ） | 個人比較は参加者間の気まずさを生む |
| §3 プッシュ通知のセグメント設計 | **SHOULD** | 「参加したがまだ0枚」セグメントへの通知が現状空白 |
| §4 友達紹介機能 | **現状維持** | EventSnapはApp Clipで既にあすけんより進んだ招待導線を持つ |
| §5 法人・団体配布チャネル | **新規提案（優先度高）** | EventSnapの「1イベント=1業務」という単位が、あすけんのB2B2Cモデルと最も相性が良い |
| §6 計測 | **SHOULD（§5より先）** | 計測が無いと§5の効果を誰も測れない |

**この資料の結論：**
EventSnapは、Rotashが目指していた「招待そのものが作品プレビューになる」体験を
App Clipで既に実現しており、あすけんの主要な成長装置（キャラクター・点数化）も
Rotashと同じ理由の大半でそのまま移植すべきではない。

**唯一かつ最大の示唆は、法人・団体配布チャネルである。** そしてRotashと違い、
EventSnapには「7人上限」のような構造的な壁がないため、**あすけんのB2B2Cモデルを
最も素直に当てはめられるのはEventSnapの方である。** ただしそれを始める前に、
今は1行も無い計測（§6）を先に用意すること。データなしに団体へ広げても、
何が起きたか誰にも分からない。
