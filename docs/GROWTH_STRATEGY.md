# EventSnap 成長構造の分析と再設計

> 対象コミット時点の実装（`Services/`・`Models/`・`Views/`・`EventSnapClip/`）を読んだ上での分析。
> 一般論ではなく、**このコードベースが今どういう成長構造を持っているか**から出発している。

---

## 0. 結論（先に）

EventSnapの成長は、**たった1本の式**に集約される。

```
R = n̄ × p_join × p_host
```

| 記号 | 意味 | 現状の推定値 | 目標値 |
| --- | --- | --- | --- |
| `n̄` | 1イベントに居合わせる「EventSnap未導入」の人数 | 5〜6人 | **15人以上** |
| `p_join` | そのうち実際に参加まで到達する率 | 0.3〜0.4 | 0.6 |
| `p_host` | 参加経験者が30日以内に「自分でイベントを作る」率 | 0.02〜0.05 | 0.15 |
| **R** | **1イベントが生む次イベント数** | **≒0.1** | **1.35** |

現状 `R ≒ 0.1` は「10回イベントが起きて、ようやく次が1回生まれる」状態で、これは**バイラルではなく減衰**である。広告を止めた瞬間に止まる。

この式が重要なのは、**やるべきことが3つしかない**と示すからだ。そして3つの中で、

- `n̄` は**機能ではなく「どのイベントを狙うか」で決まる**唯一の線形係数
- `p_join` は今**App Clipが中身ゼロの壁になっていること**で潰れている
- `p_host` は**UI上に転換点が1つも存在しない**ため、ほぼゼロのまま

以下、すべてこの3変数の話に還元して書く。

## A. 成長ループの可視化

### A-1. 現在の1周（コードに書かれている通りの姿）

| # | 段階 | 実装上の実態 | 漏れ |
| --- | --- | --- | --- |
| 1 | 最初のユーザー＝**ホスト** | `HomeView` の「新しいイベントを作成」→ `EventRepository.createEvent` | — |
| 2 | きっかけ | 「今この場の写真を全員分集めたい」 | 弱い動機ではない。**十分強い** |
| 3 | 初回価値 | `CameraView` で撮る→`PhotoRepository`が即アップ→全員のアルバムに並ぶ | **ここは完成している** |
| 4 | 巻き込まれる人 | `QRCodeView` を見せる→参加者がスキャン→`joinEvent` | **ここで大量に漏れる（後述）** |
| 5 | 参加者のメリット | 自分が撮っていない瞬間が手に入る | 明確。ただし**参加した後にしか分からない** |
| 6 | 次に使う理由 | `TimeCapsuleService`（6時間〜2週間後の一斉公開）と`NotificationService`のローカル通知 | **唯一の再訪エンジン。実装済み** |
| 7 | 次イベントでの再利用 | **導線なし** | `endEvent()` は `currentEvent = nil` にしてホームに戻すだけ |
| 8 | 増えるユーザー数 | 上の式で `R ≒ 0.1` | — |

### A-2. 1人 → N人 → 次のN人

```
        ┌──────────────── 次周回（現状ほぼ切れている）────────────────┐
        │                                                              │
   [ホスト1人]                                                         │
        │ イベント作成                                                 │
        ↓                                                              │
   [QRコード提示] ──── n̄人が読む（5〜6人）                             │
        │                                                              │
        │  ✗ App Clip＝中身ゼロの「入手してください」画面              │
        │  ✗ App Store → DL → 起動 → もう一度スキャン（5段）           │
        ↓  p_join ≈ 0.35                                               │
   [参加者 2人]                                                        │
        │ 全員で撮る → 写真が集まる → 価値を体験                       │
        ↓                                                              │
   [タイムカプセル公開通知] ← 6h〜2週間後、再訪が起きる ✓              │
        │                                                              │
        │  ✗ ここで「次」への導線が存在しない                          │
        ↓  p_host ≈ 0.03                                               │
   [次のホスト 0.06人] ─────────────────────────────────────────────────┘

   R = 5.5 × 0.35 × 0.03 ≒ 0.06〜0.1
```

**同じ図の、あるべき姿：**

```
   [ホスト1人] → [QR] → n̄=15人が読む
                    ↓  App Clip / Webで「今このイベントに何が集まっているか」が見える
                    ↓  撮りたい人だけがアプリを入れる（見るのは無料・無摩擦）
                 p_join = 0.6
   [参加者 9人] → 撮る → 写真が集まる → タイムカプセル公開で全員再訪
                    ↓
                 [イベント終了 = フィナーレ]
                 Reel配布 / 一括保存 / 「同じメンバーでもう一度」
                    ↓  p_host = 0.15
   [次のホスト 1.35人] → 次のイベントへ

   R = 15 × 0.6 × 0.15 = 1.35 > 1.0  → 自走
```

### A-3. この図から出る、非自明な結論

**EventSnapは「4人の飲み会」では絶対に自走しない。**

`n̄` は式の中で唯一の線形係数であり、`p_join` や `p_host` の改善（せいぜい2〜5倍）より、`n̄` を 5→15 にする方が確実に効く。4人の飲み会では `n̄ = 3`。`p_join`・`p_host`をどれだけ磨いても `R = 3 × 0.6 × 0.15 = 0.27` にしかならない。

→ **狙うべきイベントは、文化祭・サークル合宿・ゼミ旅行・部活の大会・結婚式・成人式**。つまり**20人以上が同じ場所に長時間いて、全員が写真を欲しがるイベント**。飲み会や少人数旅行は「使われるが増えない」市場である。

## B. 「イベント終了後」の問題

### B-1. 診断：利用理由が「消える」のではなく、「こちらから消している」

`EventRepository.endEvent()` は、`currentEvent = nil` にして `saveCurrentEventID(nil)` し、ユーザーをタイトル画面に戻す。

これは**体験のピークで幕を下ろしている**。写真が最も多く集まり、全員のテンションが最も高い瞬間に、アプリは「終わりました」と言って何も渡さない。コード上のコメントは「終了をきっかけに何かを生成する必要はない」と書いているが、成長構造の観点では**ここが唯一かつ最大の転換点**である。

### B-2. 時間軸ごとの再訪理由

| 時点 | 現状の再訪理由 | 評価 | 追加すべきもの |
| --- | --- | --- | --- |
| 直後（〜1時間） | なし（ホームに戻される） | ✗ | **フィナーレ**：Reel完成・全員に配布・カメラロール一括保存 |
| 翌日 | タイムカプセル公開（最短6h） | ◎ 実装済み | プッシュの到達確実化 |
| 1週間後 | タイムカプセル公開（最長14日） | ○ | ホーム画面ウィジェットに「1週間前のあの日」 |
| 1か月後 | **なし** | ✗ | 「次はいつやる？」の種まき。ただし**月1回まで** |
| 次のイベント時 | ユーザーが自力で思い出す必要がある | ✗ | ここが `p_host`。B-4へ |

### B-3. 各論への回答

**「写真を見ること以外に戻る理由が必要か」→ 必要。ただし"写真以外のコンテンツ"は不要。**

必要なのは「写真が**新しく**なること」。タイムカプセルはまさにこれで、**同じイベントの中に時間差で新しさが湧く**という構造になっている。EventSnap最大の発明はここ。SNS的な新規コンテンツを足す必要はない。

**「イベント履歴はどこまで重要か」→ 極めて重要。しかも今、致命的に脆い。**

`EventRepository` の履歴は `UserDefaults` の `joinedEventIDs`（上限20件）にしか存在しない。`DeviceIdentity` も `UserDefaults` 保存の端末ID。つまり——

> **機種変更・アプリ削除で、過去の思い出が全部消える。**

CloudKit側に `Event.participantIDs` はあるので、端末IDで逆引きするクエリを1本足せば復元できる。「思い出が残る」を謳うアプリでこれが無いのは、価値提案そのものへの裏切りであり、`p_host`（＝過去の体験を思い出せること）の土台でもある。

**「"自分が写っている写真"の通知は有効か」→ 有効だが、今のアーキテクチャでは実装してはいけない。**

- EventSnapに**アカウントも顔情報も無い**。参加者は `EventRepository.makeParticipants` で「参加者1」「参加者2」と表示される
- `PhotoAnalyzer` の Vision 利用は**顔検出（どこに顔があるか）であって顔認識（誰か）ではない**。Reelの構図決定用
- 実装するには顔クラスタリング＋本人同意フロー＋誤認識時の救済が要る。個人開発の規模を超え、プライバシーリスクも大きい

→ **代替で90%取れる**：`Photo.uploaderName` は既に存在する。「**〇〇さんが写真を追加しました**」で十分に再訪を生む。コスト1/50。

**「友達が追加した写真による再訪は有効か」→ 有効。ただしイベント期間中に限る。**

終了済みイベントに後から写真は追加できない仕様なので、これは実質「イベント中に離脱した人を引き戻す」通知。1イベントにつき最大2〜3回に絞ること。

### B-4. 参加者をホストへ転換する方法（`p_host`）

転換が起きるのは**次のイベントの計画が立った瞬間**であって、アプリを開いた瞬間ではない。だから「アプリ内でホストになれ」と促しても効かない。効くのは次の3つ：

1. **記憶の定着**：終了時にReelが手元に残り、カメラロールに写真が入る。「あれ、良かったな」が物理的に残る
2. **再現の容易さ**：過去イベントから「同じ名前で新しいイベント」がワンタップ。ゼロから作る心理コストを消す
3. **想起のタイミング**：終了7日後の1回だけ「次はいつ？」。それ以上は害

### B-5. SNS化のリスク評価（必ず守る境界線）

| 追加候補 | EventSnapの中核価値への影響 | 判定 |
| --- | --- | --- |
| フォロー/フォロワー | **「その場にいる人だけ」が完全に死ぬ**。イベントの外に人間関係が漏れる | **絶対禁止** |
| フィード（イベント横断） | イベントという境界が消え、ただの弱いInstagramになる | **絶対禁止** |
| いいね・コメント | 写真に優劣が生まれ、「全員が等しく撮る」が壊れる | **禁止** |
| DM | モデレーション責任が発生。個人開発では背負えない | **禁止** |
| 公開イベント検索 | 「その場にいた人だけ」の前提が崩壊 | **絶対禁止** |
| 表示名（イベント内のみ） | 匿名の「参加者1」より思い出として良い。**外には漏れない** | **可** |
| 終了後のReel配布 | 既存のEvent Reelを配るだけ。新しい社交は発生しない | **可** |

境界線の言語化：**「イベントの中で完結し、イベントが終われば関係も終わるもの」はOK。「イベントを越えて人間関係が持続するもの」はすべてNG。**

これを守る限りSNS化のリスクはない。逆にこの線を1回でも越えると、EventSnapは「機能が少ないInstagram」になり、勝ち目が消える。

## C. 5つのGrowth Loopの評価

| | Loop 1<br>イベント→参加→写真→満足 | Loop 2<br>参加者→次のイベント | Loop 3<br>写真→外部シェア→新規 | Loop 4<br>終了→思い出→再訪 | Loop 5<br>参加者→ホスト化 |
| --- | --- | --- | --- | --- | --- |
| **強さ** | ◎ 中核価値 | — | ○ | ◎ | ◎◎ |
| **自然さ** | ◎ | — | △ 撮影者の許可が要る | ◎ 時間が勝手に動く | ○ |
| **実装コスト** | 済 | — | 小（QR焼き込み） | 中（履歴のサーバー化） | 中（フィナーレUI） |
| **成長への影響** | 間接（土台） | — | 中 | 中 | **最大** |
| **UXへの悪影響** | なし | — | なし（既に許可制） | 通知過多に注意 | 押しつけがましさに注意 |
| **スパム感** | なし | — | 低（クレジット表記） | 中（通知次第） | 中（頻度次第） |
| **SNSとの競合** | なし | — | Instagramへの「持ち出し」なので**競合しない、むしろ利用する** | なし | なし |
| **本当に必要か** | 済んでいる | **不要** | **必要** | **必要** | **最重要** |

### C-1. Loop 2 と Loop 5 は同じループである

これは重要な指摘。**Loop 2「参加者が次のイベントで再利用する」は、誰かがイベントを作らない限り発生しない。** 参加者は単独ではEventSnapを使えない（`joinEvent` はQRなしには到達できず、QRはホストしか出せない）。

つまり **Loop 2 は Loop 5 の結果に過ぎず、独立したループではない**。5本あるように見えるループは、実質3本：

- **Loop 1（価値の生成）** — 完成済み。ここは触らない
- **Loop 3（外部への露出）** — 半分実装済み、あと一歩
- **Loop 4 → Loop 5（再訪から次周回へ）** — **ここが全て**

EventSnapのあらゆる成長施策は「**参加者をホストに変える**」という1点に集約して考えるべきである。

### C-2. Loop 3 の現状：広告として機能していない

`SocialCardService.drawBrandMark` は Event Reel に「EVENTSNAP」のワードマークとブランドドットを描く。設計意図は「広告ではなくフォトクレジット」。美意識としては正しい。

しかし成長構造としては、**認知は生むが行動を生まない**。Instagram のストーリーで見た人が「EVENTSNAP」という8文字から検索して App Store にたどり着く率は、極めて低い。

→ **右下に小さなQR（またはドメイン表記）を1つ足すだけ**でLoop 3は閉じる。注意点：このQRは**過去のイベントに参加させるURLであってはならない**（終わったイベントに入っても価値がない）。**アプリ入手ページ**へ飛ばすこと。

## D. 「シェア機能」と「本当にバイラルな構造」の違い

### D-1. なぜ弱い施策は弱いのか

弱い施策（招待ボタン・SNSシェアボタン・紹介キャンペーン・通知増・ポイント）はすべて、**ユーザーに「本来やりたくないこと」を追加でお願いする**構造をしている。だから転換率の掛け算で減衰する：

```
ボタンを見る 100% → 押す 3% → 相手に送る 60% → 相手が押す 20% → 相手がDL 30%
= 0.1%
```

しかも「お願い」なので、押されなかった分の摩擦（うっとうしさ）だけが残る。

### D-2. なぜ強い構造は強いのか

強い構造では、**価値を得る動作と、拡散する動作が同一**である。分離していないので、掛け算にならない。

**EventSnapのQRコードは、すでにこの構造を持っている。**

ホストはQRを「招待したいから」見せているのではない。**「自分が写っていない写真も欲しいから」見せている**。招待は目的ではなく、価値獲得の手段そのものである。だから：

- 「友達を誘おう」というCTAが要らない。**誘わないと自分が損をする**
- 参加者が増えるほど写真が増え、ホストの取り分が増える（`n̄`が大きいほど価値が高い）
- 押しつけがましさがゼロ。誘っているのは EventSnap ではなくホスト本人

これは Lapse が「5人招待しないと使えない」という強制で人工的に作った構造を、EventSnapは**体験として自然に持っている**ということだ。Lapse はこの強制で App Store 1位を取ったが「ネズミ講だ」と批判された。EventSnapは同じ強度を、批判されずに手に入れている。

**したがって EventSnap に招待ボタンも紹介キャンペーンも要らない。** 必要なのは、既に強い構造の**前後にある詰まり**を取ることだけ：

- 前の詰まり ＝ QRを読んだ人が何も見られない（`p_join`）
- 後の詰まり ＝ 参加した人がホストにならない（`p_host`）

## E. 追加すべき機能の優先順位

評価軸：解決する問題 / 強化するLoop / ユーザー心理 / 期待する行動 / 実装難易度 / 優先度 / MVP判定

### E-0.【最優先・機能ではなく修理】Universal Link と App Clip の疎通確認

- **問題**：リポジトリの `apple-app-site-association` は `TEAMID` がプレースホルダのまま。かつ App Clip の Bundle ID が `app.takaoka.com.EventSnap2.Clip` と書かれているが、READMEの記載は `app.takaoka.com.EventSnap2.AppClip` で**不一致**。この内容が本番配信されていれば、**標準カメラアプリでQRを読んでもUniversal Linkが開かない＝参加ファネルの入口が存在しない**
- **Loop**：全ループの前提
- **難易度**：極小（ファイル1つ）
- **優先度**：**P0**。他のどの施策よりも先。実機の標準カメラアプリでQRを読み、アプリ／App Clipが起動することを必ず確認する
- **MVP**：必須

---

### E-1.【P0】QRを読んだ人が「中身」を見られるようにする（`p_join`）

- **問題**：現在の App Clip（`EventSnapClipRootView` / `GetAppScreen`）は**ネットワークアクセスを一切持たない案内画面**で、イベント名すら表示できない。QRを読んだ非ユーザーが最初に見るのは「EventSnapに招待されました／App Storeへ」だけ。**価値を1ミリも見せずにインストールを要求している**
- **コード上の制約**：`EventSnapClip.entitlements` のコメント通り、App Clip に iCloud/CloudKit の entitlement は付けられない。これは事実
- **しかし**：**App Clip は普通のHTTPSリクエストは送れる**。制約は「CloudKitフレームワークが使えない」であって「ネットワークが使えない」ではない。ここが現在の実装の判断ミス
- **解**：既にある Vercel サイト（`AppLinkConfig.host`）に**読み取り専用の軽量エンドポイント**を1本立て、App Clip とブラウザの両方がそれを叩く
  - `GET /api/event/{id}` → イベント名・参加人数・写真枚数・公開済みサムネイル数枚
  - サーバー側は CloudKit Web Services（public DB は API トークンで読める）でも、書き込み時にVercel KV等へミラーする形でもよい。**ただし CloudKit Web Services の現行サポート状況は着手前に必ず検証すること**
- **見せるもの**：「〇〇の写真が **47枚** 集まっています」＋ サムネイルのぼかしグリッド ＋ 「撮って参加するにはアプリを入手」
- **心理**：「入れてと言われたから入れる」→「**もう始まっている、混ざりたい**」
- **期待する行動**：`p_join` 0.35 → 0.6
- **思想との整合**：**「見るのは無摩擦、撮るのはアプリ」。参加（＝撮影）は依然としてQRを読んだ人だけ**。「その場にいる人だけ」は1ミリも壊れない
- **難易度**：中（Web側1本＋App Clip画面1枚）
- **MVP**：**入れるべき**

> 市場データがこの重要性を裏づける：2026年の調査では、QR経由の写真アップロードはアプリ経由の**4.3倍**。競合（Kululu / GuestCam / Fotify）は全員「アプリ不要」で戦っている。EventSnapが「インストール必須」のまま戦うのは、100m走を靴紐で縛って走るのに等しい。

### E-2.【P0】イベント終了を「フィナーレ」にする（`p_host`）

- **問題**：`endEvent()` が価値のピークで体験を打ち切っている。Loop 5 の転換点がUI上に存在しない
- **解**：終了時に全画面のフィナーレを出す
  1. そのイベントの Event Reel を表示（既に `ShareCollageBuilder` が生成済み）
  2. 「**写真をまとめて保存**」（`AlbumView` に単体保存は実装済み。一括にするだけ）
  3. 「**シェア**」（`SocialCardShareView` の `ShareLink` を再利用）
  4. 「**同じメンバーでもう一度**」＝ 同名の新規イベント作成＋QR表示へ直行
  5. 「まだタイムカプセルが N枚 残っています」→ 再訪の予告
- **心理**：達成感の頂点で「もう一回やりたい」と「持ち帰れた」を同時に置く
- **難易度**：中（既存部品の組み合わせ。新規ロジックはほぼ不要）
- **MVP**：**入れるべき**

### E-3.【P1】表示名をイベントに保存する

- **問題**：`EventRepository.makeParticipants` が自分以外を「参加者1」「参加者2」と表示。`DeviceIdentity.displayName` はローカルにしかなく、CloudKitに保存されていない
- **解**：`Event` に `participantNames: [String]` を追加（`Photo.uploaderName` と同じ扱い）。初回参加時に名前を1回だけ聞く。アカウントは作らない
- **効く先**：思い出の質（10年後に「参加者3」では意味がない）／通知文言／`p_host` の心理的下地
- **難易度**：小
- **MVP**：**入れるべき**

### E-4.【P1】参加履歴のサーバー側復元

- **問題**：履歴が `UserDefaults` の `joinedEventIDs` のみ。機種変更で全消失
- **解**：`Event.participantIDs` を端末IDで検索するクエリ（要 Queryable インデックス）＋ 起動時のマージ
- **効く先**：Loop 4 の土台。「思い出が残る」という約束の履行
- **難易度**：中
- **MVP**：**入れるべき**（ユーザーが増えてからでは手遅れになる種類の問題）

### E-5.【P1】Event Reel に「入手用QR」を焼き込む

- **問題**：外部シェア画像がブランド表記だけで、行動に繋がらない
- **解**：`SocialCardService.drawBrandMark` の隣に小さなQR。飛び先は**アプリ入手ページ**（過去イベントではない）
- **難易度**：小（`QRCodeService` 流用）
- **MVP**：入れるべき

### E-6.【P2】「思い出ウィジェット」

- 既に `EventSnapWidget` と `EventSnapSharedState` がある。今はイベント中のReelしか出していない。終了後は「1週間前のあの日」を出す
- **心理**：Locket と同じ構造 ＝ **アプリを開かせずに価値を届け、結果として開かせる**
- **難易度**：小〜中
- **MVP**：後回し可

### E-7.【P2】タイムカプセル公開通知の到達確実化

- **問題**：`NotificationService` はローカル通知方式（CloudKitに定時実行が無いための正しい回避策）。ただし**各端末がアプリを開いて予約している必要がある**。イベント後に一度もアプリを開かなかった参加者には届かない可能性がある
- **解**：silent push 受信時の予約再実行を確実にする／64件上限の運用を複数イベント跨ぎで検証
- **難易度**：中
- **MVP**：後回し可（ただしLoop 4の生命線なので、P2の中では最優先）

### E-8.【P3】終了7日後の「次はいつ？」

- 月1回まで。これ以上は通知疲れで逆効果
- **MVP**：後回し

## F. 競合比較 —「次のユーザーを連れてくる構造」で見る

機能ではなく**構造**で比較する。

| サービス | ユーザーが次のユーザーを連れてくる構造 | エンジン | EventSnapが取るべきもの |
| --- | --- | --- | --- |
| **BeReal** | 既存の友達グラフ前提。**毎日ランダムな時刻の一斉通知**で全員を同時に動かす。獲得自体はアプリ外の口コミ | **時間の同期性** | **既に持っている**（タイムカプセル）。BeRealはこれで2025年コホートの6か月継続率71%（WhatsApp 83%に次ぐ2位、TikTok 58%・Snapchat 52%を上回る）。**「全員が同時に同じものを見る」は最強の再訪装置**だと実証されている |
| **Locket** | ウィジェットで**アプリを開かせずに**友達の写真が届く。届いた側が入れたくなる | **ホーム画面の占有** | `EventSnapWidget` は既にある。**終了後も使う**（E-6） |
| **Lapse** | **強制招待5人**。1か月でApp Store 118位→1位。ただし「ネズミ講」と批判 | **招待の強制** | **真似してはいけない。既に自然な形で持っている**（QR＝招待が価値獲得と同一）。学ぶのは「招待をオンボーディングの中心に据えた」という配置だけ |
| **Instagram / Snapchat** | 外部に持ち出せる成果物＋既存グラフ | **持ち出せる作品** | Event Reel。**競合ではなく配布チャネルとして使う**（E-5） |
| **Google Photos 共有アルバム** | ほぼゼロ摩擦（アカウントは全員持っている）。だが**イベント感・リアルタイム性・盛り上がりがゼロ** | 摩擦の低さのみ | 摩擦の低さは学ぶ（E-1）。体験は真似しない |
| **LINEアルバム（日本での真の敵）** | 全員が既に入れている。**摩擦ゼロ** | デフォルトであること | 勝ち筋は「撮った瞬間に共有される」。LINEは**後から選んで送る手間**があり、その場のリアルタイム性と「他人が撮った自分」が無い |
| **Kululu / GuestCam / Fotify 等** | **アプリ不要・QRとWebだけ**。有料SaaS（ホストが払う） | 摩擦ゼロ | **ここが最大の脅威**。ただし彼らは参加者にプロダクトが残らない ＝ **ループが1周で終わる** |

### F-1. EventSnapの構造的な位置

競合を2軸で置くと、EventSnapが取るべき位置がはっきりする。

```
                    参加者にプロダクトが残る（次周回がある）
                                  ↑
              EventSnap（今）     │     ★ EventSnapが行くべき場所
              参加に摩擦が大      │     見るのは無摩擦・撮るのはアプリ
                                  │
   摩擦 高 ←──────────────────────┼──────────────────────→ 摩擦 低
                                  │
                                  │     Kululu / GuestCam / Fotify
                                  │     LINEアルバム / Google Photos
                                  ↓
                    参加者に何も残らない（1周で終わる）
```

- Web専業サービスは**摩擦ゼロだが1周で終わる**（`p_host` が構造的にゼロ。ホストは毎回新しく獲得するしかない）
- EventSnapは**次周回の可能性を持つ唯一の形**だが、今は入口の摩擦でその可能性に到達できていない
- **右上に行けば勝てる。**「見るのはWeb/App Clipで無摩擦、撮るのはアプリ」というハイブリッドが、この2軸を両取りする唯一の設計である

### G-1. 候補の評価

| --- | --- | --- | --- | --- |
| DAU / MAU | ✗ イベント型アプリでは構造的に低い。低くて正常 | ✗ | 高 | 却下 |
| インストール数 | ✗ 参加させられただけの数を含む | ✗ | 高 | 却下 |
| 1イベントあたり写真数 | △ | ◎ | 中 | **入力指標として採用** |
| 1イベントあたり参加者数（`n̄`） | ○ | ○ | 低 | **入力指標として採用** |
| ホスト再利用率 | ○ | △ | 低 | 入力指標 |
| 参加者→次回ホスト転換率（`p_host`） | ◎ | △ | 低 | **入力指標として採用** |
| **イベント→次イベントの発生率** | **◎** | ○ | 低 | **★ North Star** |

### G-2. North Star Metric（1つ選ぶ）

> ## R30 ＝ 成立イベント再生産率
> **「1件の成立イベントが、30日以内に生む成立イベントの数」**
>
> **成立イベント**の定義：参加者3人以上 かつ 写真20枚以上 が集まったイベント
> （「作っただけ」「1人だけ」のイベントを数えないためのガードレール）

**なぜこれが最良か：**

1. **成長の定義そのもの**。`R30 ≥ 1.0` なら広告ゼロで自走、`< 1.0` なら減衰。閾値に意味がある指標は珍しい
2. **価値を内包している**。「成立」の条件（3人以上・20枚以上）を満たさないイベントは分子にも分母にも入らないので、**質を落として数を稼ぐことができない**
3. **完全に分解できる**：`R30 = n̄ × p_join × p_host`。数字が悪いとき、3つのどれが悪いのか必ず特定できる
4. **イベント型プロダクトの実態に合っている**。DAUを追うと「毎日開かせる機能」を作りたくなり、SNS化して自滅する。R30を追う限り、**イベントを増やす方向にしか最適化できない**

**ダッシュボードの構成：**

```
North Star   R30 = 0.42          （目標 1.00）
             ├─ n̄      = 6.2人   （目標 15人）  ← どのイベントを狙うか
             ├─ p_join = 0.38    （目標 0.60）  ← App Clip / Web
             └─ p_host = 0.18    （目標 0.15）  ← フィナーレ / 履歴 / 名前

ガードレール  成立率（作成イベントのうち成立に至った割合）
             通知オプトアウト率
             1イベントあたり写真数
```

**計測に必要な追加実装**は小さい：`Event` に `createdBy` の過去参加履歴が辿れればよい。`creatorID`（端末ID）と `participantIDs` は既にあるので、**「このイベントの `creatorID` は、過去30日以内の別イベントの `participantIDs` に含まれていたか」**を集計するだけで `p_host` が出る。**新しいトラッキング基盤は要らない。**

## H. 最終提案

### 絶対にやる（4つ）

| # | やること | 効く変数 | 理由 |
| --- | --- | --- | --- |
| 1 | **AASA / Universal Link / App Clip の本番疎通を直す** | 全部 | 現状、標準カメラアプリからQRが機能しない疑いが濃い。**入口が無ければ他の全施策の効果はゼロ** |
| 2 | **QRを読んだ人に「今このイベントに集まっているもの」を見せる**（App Clip＋Web、HTTPS経由） | `p_join` | 価値を見せずにインストールを要求している現状が、ループ最大の漏れ。思想（その場にいる人だけ撮れる）は一切壊さない |
| 3 | **イベント終了をフィナーレにする**（Reel配布・一括保存・「同じメンバーでもう一度」） | `p_host` | Loop 5の転換点がUI上に存在しない。既存部品の組み合わせで作れる |
| 4 | **参加履歴のサーバー側復元＋表示名** | `p_host`・Loop 4 | 機種変更で思い出が消えるのは、価値提案そのものへの裏切り。ユーザーが増えてからでは手遅れ |

### できればやる（4つ）

| # | やること | 効く変数 |
| --- | --- | --- |
| 5 | Event Reel に入手用QRを焼き込む | Loop 3 |
| 6 | 終了後の「思い出ウィジェット」 | Loop 4 |
| 7 | タイムカプセル公開通知の到達確実化 | Loop 4 |
| 8 | ターゲットを20人以上のイベント（文化祭・サークル・合宿）に絞ったオンボーディング文言・ホスト向けガイド | `n̄` |

### 今はやらない（10）

| # | やらないこと | 理由 |
| --- | --- | --- |
| 1 | 「あなたが写っている写真」通知（顔認識） | アカウントも顔情報も無い。実装コスト・プライバシーリスクが便益に見合わない。`uploaderName` 通知で90%代替できる |
| 2 | フォロー / フォロワー | **「その場にいる人だけ」が死ぬ。最大の差別化の自殺** |
| 3 | イベント横断フィード | 同上 |
| 4 | いいね / コメント | 写真に優劣が生まれ「全員が等しく撮る」が壊れる |
| 5 | DM / チャット | モデレーション責任を個人開発で背負えない |
| 6 | 招待コード / リンク参加 | **思想違反**。QRのみという制約がプロダクトの魂 |
| 7 | 招待キャンペーン・紹介ポイント | D章の通り、構造が既に強いので不要。むしろ純度を下げる |
| 8 | 公開イベントの検索・発見 | 「その場にいた人だけ」の前提が崩壊 |
| 9 | AIフィルター・美肌加工 | 差別化にならず、Vision の用途（Reelの構図）と混同される |
| 10 | Android版・課金・汎用アルバム化 | `R30 ≥ 1.0` を1つの市場で証明してから。証明前の横展開は資源の分散 |

## 最後に：EventSnapの成長ループ 1枚

```
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  【誰が】   20人以上が集まるイベントの主催者（文化祭・サークル・合宿）   │
│      │                                                                 │
│  【何をして】 EventSnapでイベントを作り、その場でQRコードを見せる        │
│      │        ※ 招待したいからではなく、自分が写っていない写真が        │
│      │          欲しいから見せる ＝ 価値獲得と拡散が同一動作             │
│      ↓                                                                 │
│  【何を得て】 撮った瞬間に全員のアルバムへ。自分が見ていない            │
│      │        角度の自分、自分がいない時間の仲間が集まる                 │
│      ↓                                                                 │
│  【誰を巻き込み】 QRを読んだ n̄ 人。読んだ瞬間に                         │
│      │            「もう47枚集まっている」が見える（無摩擦）             │
│      │            → 撮りたい人がアプリを入れて参加（p_join）             │
│      ↓                                                                 │
│  【次に何が起きる】                                                     │
│      │                                                                 │
│      ├─① イベント終了 = フィナーレ                                     │
│      │     Reelが全員の手元に残り、写真がカメラロールに入る              │
│      │     → 外部SNSへ持ち出される → EventSnapが人目に触れる            │
│      │                                                                 │
│      ├─② 6時間〜2週間後、タイムカプセルが全員に一斉公開                 │
│      │     → イベントが終わった後に、イベントが更新される                │
│      │     → 全員が同時に戻ってくる（BeRealと同じ「時間の同期性」）      │
│      │                                                                 │
│      └─③ 次のイベントの予定が立った日                                   │
│            「同じメンバーでもう一度」がワンタップで残っている            │
│            → 参加者だった人が、今度はホストになる（p_host）              │
│                          │                                             │
│                          └──→ 【誰が】へ戻る                           │
│                                                                        │
│              R = n̄ × p_join × p_host ≥ 1.0 で自走                      │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**この図の要点は、新しい機能が1つも登場しないことである。**

QR・撮影即共有・タイムカプセル・Event Reel・ウィジェット——ループを回すために必要な部品は、すでに全部このリポジトリの中にある。足りないのは部品ではなく、**部品と部品の間の接続**だ。

- QRと「見る」の間 ＝ App Clipが中身ゼロ
- 「終わり」と「次」の間 ＝ フィナーレが無い
- 「思い出」と「未来」の間 ＝ 履歴がローカルにしかない

**この3つの接続を繋ぐことが、EventSnapを流行らせるということである。**
