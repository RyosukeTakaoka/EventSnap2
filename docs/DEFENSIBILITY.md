# Defensibility Map — 「アイデア」ではなく「模倣困難な仕組み」

[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md)〜[`FRAME_CHANGE_STRATEGY.md`](FRAME_CHANGE_STRATEGY.md) までの5本は、
「他社の成功事例から何を借りるか」「EventSnap自身の前提をどう変えるか」を扱ってきた。

この資料は問いの立て方が違う。**「EventSnapが成功した後、競合が機能を完全コピーしたら何が残るか」**
を先に考える。三井越後屋の「現金掛け値なし」が単体の発明ではなく、店頭販売・現金取引・定価・
切り売り・新しい顧客層・広告・検証を一体化した**相互依存する仕組み**だったからこそ、
競合が値下げだけを真似ても同じ経済構造にはならなかった——という指摘に基づく。
（このフレーム自体はユーザーからの分析提供。本資料はそれをEventSnapの現状のコードと
既存Docsに照らして具体化したものである。）

**結論を先に書く。** EventSnapは「プロダクト」としての完成度が高い
（QR参加・自動共有・タイムカプセル・Event Reel・App Clip・Widget/Live Activityが
一通り実装済み）。**しかしその機能群のほとんどは、大手が本気を出せばコピーできる。**
本当の防御は機能ではなく、**「主催者が次のイベントでもEventSnapを選ぶ」という関係**
にある。

---

## 1. もし競合がコピーしたら

Google・LINE・Instagramのいずれかが「イベント用の自動共有アルバム」を作ったとする。
QR参加、自動アップロード、AIによるベストショット選定、SNS用画像生成、ウィジェット——
**これらは技術的にはすべて模倣可能である。** 特に `EventReelPhotoSelector` の
写真選定ロジック（撮影者の多様性・色味・顔・Saliency・時間的分散を見て選ぶ）は
作り込まれているが、**「Google/LINE/Instagramが同じものを作れない」わけではない。**

**→ だから機能の作り込みだけに安住してはいけない。** 求めるべきは、
コピーされても揺るがない**5つの層**である。

---

## 2. 防御の5層

### 層①：UX（撮るだけ） — コピー可能。土台として維持する

「投稿ボタンが無い」「撮影と同時に全員のアルバムに並ぶ」というUXは、
競争軸を「どの共有アルバムが便利か」から「イベント中の写真行動をどこまで
意識させずに済ませられるか」へ変える良い設計だが、**それ自体は模倣可能**であり、
単独では防御にならない。

### 層②：Event Reel — 「AI写真編集」ではなく「イベントの作品化」へ

現在のEvent Reelは「良い写真をAIが選んでレイアウトする」という設計だが、
これは**「AI写真編集アプリ」の一種として見れば、競合にも作れる。**
目指すべきは、**「写真→作品」ではなく「イベント→作品」**という一段上の変換である。

```
今のEvent Reel：良い写真を数枚選んで、テンプレートに流し込む
目指す姿：文化祭ならその1日の時間軸、旅行ならその数日間の物語、
         卒業ならそのメンバーで過ごす最後の日——という
         「そのイベントでしか作れない構成」を作品に反映する
```

これは新しいMUSTを今すぐ追加する提案ではないが、Event Reelの進化の方向性として、
テンプレート追加より先に**「イベントの文脈（時間軸・目的）を作品に織り込む」**
方向を優先することを記録しておく。

### 層③：主催者ネットワーク — 最も弱く、最も重要な層

`ASKEN_GROWTH_CASE_STUDY.md` §5・[`MIRO_GROWTH_CASE_STUDY.md`](MIRO_GROWTH_CASE_STUDY.md) §4 で既に
法人・団体展開を検討したが、この資料は**より具体的な問い**を立てる。
**「同じ主催者が、次のイベントでもEventSnapを選ぶか」**である。

```
文化祭実行委員 → EventSnap導入 → 300人参加 → 来年の文化祭 → またEventSnap
サークル代表 → 新歓で使用 → 合宿 → 忘年会 → 卒業旅行 → 毎回EventSnap
```

ここで初めて、「イベント単位の一時利用アプリ」なのに**継続利用のネットワーク効果**が
生まれる。現状この層は**ゼロ**である（計測が無いため、Repeat Organizerが
何%いるかすら分からない。§4で扱う）。

### 層④：イベント履歴の蓄積 — 主催者にとっての資産化

`EventSwitcherView`（過去イベントの履歴）は既に実装されているが、現状は
単なる過去イベントのリストである。目指す姿は、主催者にとって
**「2026 文化祭 → 2026 体育祭 → 2026 修学旅行 → 2027 文化祭」**という
**その団体のイベント史そのものがEventSnap上に蓄積される**状態である。
ここまで行けば、主催者がEventSnapから離れるコストが上がる——
**写真が移行できないからではなく、「この団体の歴史がここにある」からである。**

### 層⑤：イベント運営インフラ化 — Distributionそのものを製品にする

最終的に目指すのは、QR配布→写真収集→作品化→共有→次回イベントという
**一連の運営フローをEventSnapが丸ごと担うインフラ**になることである。
ここまで行けば、主催者にとって乗り換えるコストは「アプリを変える」ではなく
**「運営フローそのものを作り直す」コスト**になる。これが三井越後屋の
店舗網・仕入れ網に相当する、EventSnapにとっての「システム」である。

## 3. Defensibility Map

| 資産 | コピー難易度 | 現在 | 1年後（目標） |
|---|---|---|---|
| QR参加・自動共有UX | 低 | ○（実装済み） | ○（維持するが単独では防御にならない） |
| App Clip・Widget/Live Activity | 低〜中 | ○（実装済み） | ○ |
| Event Reelの写真選定AI | 中 | ○（実装済み） | △（コピーされうる前提で次の層へ投資） |
| イベントの物語を反映したEvent Reel | 中〜高 | ×（構想段階） | △ |
| 主催者ネットワーク（Repeat Organizer） | 高 | ×（計測すら無い） | △〜○ |
| イベント履歴の蓄積（団体単位） | 高 | ×（個人の参加履歴のみ） | △ |
| イベント運営インフラとしての乗り換えコスト | 非常に高 | ×（存在しない） | × |

**読み方：** 現在○が付いている資産（UX、App Clip、Event Reel）はコピー難易度が
低〜中でしかない。**今の完成度の高さに安住せず、×の層（主催者ネットワーク・
イベント履歴・運営インフラ化）への投資を始めることが、この表の結論。**

## 4. 「ユーザー」ではなく「イベント主催者」を中心に据えた計測

`ASKEN_GROWTH_CASE_STUDY.md` §6 で「計測が1行も無い」ことを既に指摘した。
この資料はそれを**具体的な6指標**まで落とし込む。

| # | 指標 | 定義 | 何を診断するか |
|---|---|---|---|
| 1 | Join Rate | QRを見た人のうち参加した割合 | 入口の摩擦 |
| 2 | First Photo Rate | 参加者のうち1枚でも撮った割合 | 参加から行動への転換 |
| 3 | Contribution Rate | 参加者のうち写真を撮った人の割合 | イベント内での能動性 |
| 4 | Reel Generation Rate | イベントのうちEvent Reelが生成された割合 | コア価値（層②）が機能しているか |
| 5 | Reel Share Rate | 生成されたReelのうち外部共有された割合 | K（`ASKEN_GROWTH_CASE_STUDY.md` §5と接続） |
| 6 | **Repeat Organizer Rate** | 同じ主催者が次のイベントでもEventSnapを使った割合 | **層③そのもの。最重要指標** |

**指標6が最も重要である。** 普通のアプリなら「7日後リテンション」を見るが、
EventSnapのようなイベント単位アプリでは、**個人が7日後に戻るかではなく、
主催者が3か月後に次のイベントを作るか**を見るべきである。
`ASKEN_GROWTH_CASE_STUDY.md` §0 が既に整理した通り「継続主体は個人ではなく
イベント主催者・団体」という認識と、この指標は直接対応する。

**→ 判定：MUST（新規提案）。** 実装はCloudKitのレコード数を集計する
読み取り専用スクリプトで足り、アプリ本体の変更は不要
（Rotashの`tools/rotash-stats.py`と同型のアプローチ）。

## 5. 20〜50イベントをシーン別に検証する

Rotash向け資料（[`DEFENSIBILITY.md`](https://github.com/RyosukeTakaoka/Rotash/blob/main/docs/DEFENSIBILITY.md) §4）と同じ発想を、
EventSnapのシーンに当てはめる。`ASKEN_GROWTH_CASE_STUDY.md` §4 で
LATER判定した「シーン別コンテンツ」を、**先に検証の単位として使う。**

| シーン | イベント数 |
|---|---|
| 学校行事（文化祭・体育祭等） | 10 |
| 友達旅行 | 10 |
| 誕生日・パーティー | 5 |
| 部活・サークル | 5 |
| その他 | 5 |

§4の6指標をシーン別に見ることで、「EventSnapは何に使われるプロダクトなのか」が
実数で分かる。もし学校行事だけJoin Rate・Reel Generation Rate・Repeat Organizer Rateの
すべてで頭一つ抜けているなら、**「EventSnap for school events」まで絞り込む判断**が
選択肢になる。市場を狭めることは縮小ではなく、**最初の支配領域を作ること**である。

学校イベントが有力と見る理由（構造的な適合）：人数が多い・全員同じ場所にいる・
イベント時間が決まっている・写真が大量発生する・参加者間に既存の関係性がある・
主催者がいる・毎年繰り返される・「卒業」のような一度きりの瞬間がある。
**文化祭→体育祭→修学旅行→卒業という連続利用が作れれば、層③④が一気に強くなる。**

**→ 判定：MUST（§4の計測と同時に着手）。**

## 6. コードを読んで見つかった、層⑤を静かに損なっている実装

`Services/PhotoRepository.swift` を実際に読むと、**タイムカプセルの約束を
静かに破りうる経路**が実装されている。README・`TimeCapsuleService.swift`は
「`revealDate`までは撮影者本人を含め誰にも表示しない」「手動で早めて公開する
経路は無い」と明記しているが、**実際には1つだけ経路がある。**

```
1. ユーザーがタイムカプセル写真を撮る（この時点でisShareOK=falseかつisTimeCapsule=true）
2. 後から setShareOK(true) を呼ぶ（isTimeCapsuleには一切影響しない、と明記されている）
   → isShareOK=true かつ isTimeCapsule=true の両立状態になる
3. 他の参加者の写真も含めてシェアOK写真が既定枚数たまり、新しいEvent Reelが
   ビルドされるタイミングが来る
4. releaseSharedTimeCapsules が呼ばれ、対象の写真は
   「revealDateに関わらず問答無用で」（コード内コメントより）公開される
```

これは**バグではなく意図された仕様**である（`PhotoRepository.swift` 200〜214行に
明記：「イベント直後〜イベント中の共有価値を優先すると決めている」）。
しかし**ユーザーの心理的な契約**と食い違うリスクがある：

> タイムカプセルに「最長2週間」隠したはずの写真が、**自分がシェアOKに切り替えた
> 直後、他の参加者の投稿ペース次第で、数分後に公開されることがありうる。**
> これは「後で公開にしたのに、勝手に今公開された」という体験になりかねない。

**なぜこれが§5の「主催者ネットワーク」に関わるのか：** 学校行事や結婚式のような
一生に一度に近いイベントで主催者に信頼してもらうには、**「約束した通りに動く」**
という基本的な信頼性が前提になる。タイムカプセルの公開タイミングが
ユーザーの想定と食い違いうる実装は、**層③（主催者が次回も選ぶ）を静かに損なう
リスクがある。**

**→ 判定：MUST（機能追加より先に整理）。** 対応の方向性の選択肢（実装はまだしない）：
- (a) `setShareOK(true)` をタイムカプセル写真に対して呼んだ時点で、
  「revealDateより早く公開される可能性があります」という確認を挟む
- (b) タイムカプセル写真への事後的なシェアOK変更自体を禁止し、
  「今は共有せず、公開後にあらためてシェアOKにしてください」という導線にする
- (c) 現状の「シェア優先」の仕様自体は変えず、**タイムカプセル選択時にその旨を
  明示する**（「シェアOKに変更すると、早めに公開されることがあります」という
  一文をUIに追加するだけの軽い対応）

いずれもコード全体を変える規模ではなく、**次に着手する際に選択肢として検討する**
位置づけで記録する。

## 7. 今すぐやること・まだやらないこと

**MUST（今すぐ着手すべき、実装コストが小さい順）：**
1. §6のタイムカプセル/シェアOK整合性——最低限(c)の警告表示から
2. §4の計測6指標。CloudKit集計スクリプト（アプリ変更不要）
3. §5のシーン別20〜50イベント検証

**引き続き検討（新しい実装ではなく、方向性の確認）：**
- 層②（Event Reelの「イベントの物語化」）は、テンプレート追加より優先する
- 層③④（主催者ネットワーク・イベント履歴）は、§4の計測結果が出てから設計する

**まだやらないこと（既存DON'Tの再確認、`GROWTH_STRATEGY.md`のJ章相当の原則と同じ）：**
- 公開フィード・フォロワー・いいねランキング・個人投稿ランキング
- 無関係な人のイベント閲覧・TikTok型レコメンド（[`LOCKET_GROWTH_CASE_STUDY.md`](LOCKET_GROWTH_CASE_STUDY.md) §3で既に否定）
- 広告（[`TIMETREE_GROWTH_CASE_STUDY.md`](TIMETREE_GROWTH_CASE_STUDY.md) §5、[`MIRO_GROWTH_CASE_STUDY.md`](MIRO_GROWTH_CASE_STUDY.md) §1で既に否定）
- 「毎日開いてもらうため」の無理な機能・AIキャラクター（[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md) §1で既に否定）

## 8. まとめ — Rotashとの対比

同じ開発者による2つのアプリは、防御すべき層の重心が異なる。

| | Rotash | EventSnap |
|---|---|---|
| 基本単位 | 7人 | イベント |
| 周期 | 毎週 | イベントごと（本質的に一過性） |
| 最大の問題 | 初回グループ形成（3人到達率） | **イベント後の離脱**（次のイベントで戻らない） |
| 最大の防御候補 | グループの関係履歴 | **主催者・イベントのネットワーク** |
| 強くすべき相手 | 参加者7人 | **主催者** |

**Rotashは「人間関係」側に、EventSnapは「イベント運営」側に防御を寄せる。**
これが2つのアプリの差別化の軸である。

EventSnapは今、**「開発フェーズ」から「検証→特定シーンの支配フェーズ」へ移るタイミング**
にある。目指すのは「EventSnapというアプリを使ってもらう」ことではなく、
**「イベント主催者が次のイベントでもEventSnapを選ぶ」状態**——
これができて初めて、三井越後屋の「機能そのものではなく、商売の仕組みで勝つ」に近づく。
