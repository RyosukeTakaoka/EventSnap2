# CloudKit スキーマ変更手順（タイムカプセル / Event Reel）

このリリースで CloudKit のレコードに **4つのフィールドを追加**しました。
コード側は追加フィールドが無くても動くように書いてありますが、
**Dashboard でフィールドを作らないと新機能は動きません**。

---

## 1. 追加するフィールド

### `Event` レコードタイプ

変更なし。招待コードは実装しないため、追加フィールドはありません。

> 参加経路は **QRコードの読み取り（App Clip / Universal Link）だけ**です。
> 文字列を伝えるだけで参加できる手段を作ると「その場に居合わせた人だけの集まり」
> という前提が崩れるため、意図的に用意していません。

### `Photo` レコードタイプ

| フィールド名 | 型 | インデックス | 用途 |
| --- | --- | --- | --- |
| `isTimeCapsule` | Int(64) | 不要 | 遅延公開の対象か（0/1） |
| `revealDate` | Date/Time | Sortable（任意） | 公開予定日時 |
| `isShareOK` | Int(64) | 不要 | SNSシェアを本人が許可したか（0/1） |
| `uploaderName` | String | 不要 | 通知の「〇〇さんの」に使う表示名 |

`Photo` 側は現状クライアントで絞り込んでいるので Queryable は不要です。
`revealDate` はサーバー側で並べ替えたくなった時のために Sortable にしておくと後が楽です。

> `Photo` レコードは基本的に作成後は書き換わりませんが、**`isShareOK` だけは例外**で、
> 撮影後に変更できます（`PhotoRepository.setShareOK`）。間違えてONにした・写っている人
> から削除希望があった、といったケースを想定しています。更新は既存レコードを
> `id` で取得してから上書きする方式のため、`id` は Queryable にしておいてください。
> `isTimeCapsule`・`revealDate` はこの経路では一切変更されません
> （タイムカプセルの仕様には影響しません）。

**Event Reel（旧シェアコラージュ）は CloudKit に一切保存しません。** 各端末のローカルに
保存し、参加者全員が同じ「シェアOKの写真」という材料から同じ結果を組み立てる設計です
（`ShareCollageStore`）。そのため `isShareOK` が事後変更可能になっても、
Event Reel側のスキーマ変更は不要です。

## 2. Development 環境への反映

1. [CloudKit Console](https://icloud.developer.apple.com/dashboard/) を開く
2. コンテナ `iCloud.app.takaoka.com.EventSnap2` を選択
3. **Schema → Record Types** で `Photo` を開く
4. `Add Field` から上表の4つを追加
5. `id` が Queryable になっていることを確認（なければチェックを入れる）
6. `Save Changes`

> ⚠️ 開発中に一度アプリを実機で動かすと、CloudKit が
> 送信されたレコードから**フィールドを自動生成する**ことがあります。
> ただし自動生成ではインデックスが付かないので、Queryable は手で付ける必要があります。

---

## 3. Production 環境への反映

Development のスキーマは**そのままでは本番に反映されません**。

1. CloudKit Console 右上の環境セレクタが `Development` になっていることを確認
2. **Deploy Schema Changes...** ボタンを押す
3. 差分（追加される4フィールドとインデックス）が一覧で出るので内容を確認
4. `Deploy` を実行

### 注意点

- **フィールドの追加は後方互換な操作**なので、既に配信済みのアプリが壊れることはありません。
  古いアプリは知らないフィールドを単に無視します。
- 逆に **フィールドの削除・型変更・リネームは Production では不可**です。
  一度デプロイしたら消せないので、名前は今のうちに確定させてください。
- Deploy は数分かかることがあります。完了前に本番アプリを配信しないでください。

### 配信順序（重要）

```
1. Development でスキーマを追加
2. Development 環境のビルドで動作確認
3. Production へ Deploy Schema Changes
4. デプロイ完了を確認
5. App Store へアプリを提出
```

3 と 5 を逆にすると、新アプリが本番で
`Unknown field 'isTimeCapsule'` を出してタイムカプセルとシェアが動きません。

## 4. 既存データへの影響

| 対象 | 挙動 |
| --- | --- |
| v1で保存された `Photo`（新フィールドなし） | `isTimeCapsule=false` / `isShareOK=false` として読まれる。＝**即時公開・シェア不可**で、これまでと全く同じ扱い |

マイグレーションスクリプトは不要です。既存レコードは触りません。

## 5. 既知の制約

### 未公開写真のアセットURLについて

CloudKit の **Public Database にはフィールド単位のアクセス制御がありません**。
そのため、未公開のタイムカプセル写真も `imageAsset` の URL 自体はレコードに含まれます。

- アプリは `revealDate` を見て未公開の画像を**ダウンロードしません**
- ただし CloudKit API を直接叩ける人が URL を取り出すことは理論上可能です

「サプライズを守る」程度の用途としては十分ですが、**厳密な秘匿が要件になる場合は
サーバー側で公開時刻までアセットを配らない仕組み**（Cloud Functions 相当のバックエンド）が必要です。
現時点の仕様では許容範囲と判断しています。

### タイムカプセルは「個人機能」ではなく「イベント参加者全員で共有する体験」

タイムカプセル写真は **削除されません**。また `revealDate` までは **撮影者本人を含め、
誰にも表示しません**。参加者全員が同じ枚数・同じ待ち時間を共有し、公開の瞬間に
全員へ通知が届く（LINE通知のように突然思い出が届く）体験を狙っています。

| 出来事 | タイムカプセルへの影響 |
| --- | --- |
| 一定時間の経過（24時間など） | **何も起きない**。時間切れで消える仕組みは存在しない |
| イベントの終了（手動）／日付が変わる | **何も起きない**。公開予定はそのまま残る（自動終了の仕組み自体が無い） |
| `revealDate` の到来 | 公開される。参加者全員のローカル通知が鳴る |

**手動で公開を早める経路はありません**。撮影時点で **シェアOKを選んだ写真はそもそも
タイムカプセルの選定対象になりません**（`TimeCapsuleService.decideRevealDate`）。
シェアOKを付けていない写真は、いつまでも `revealDate` まで参加者全員から伏せたままです。

### 公開通知の仕組み

CloudKit には「指定時刻にサーバー側で処理を走らせる」機能がありません
（`CKSubscription` はレコードの作成・更新でしか発火しない）。

そのため公開通知は **各端末のローカル通知**で実現しています。

```
写真アップロード（revealDateが確定）
  → CKQuerySubscription のサイレントプッシュが全メンバーに届く
  → 各端末が写真一覧を取り直し、未公開分の公開時刻にローカル通知を予約
  → 予約時刻に各端末で通知が鳴る
```

アプリがフォアグラウンドに戻るたびにも予約し直すので、
サイレントプッシュを取りこぼしても次回起動で復帰します。

**制約**: iOS が1アプリに許す保留中ローカル通知は **64件**までです。
`NotificationService.maxScheduled = 56` は **1イベントあたり**の上限で、
公開が近いものから予約します。複数イベントに参加していると合計で64件を
超えうるものの、直近に鳴るべき通知から埋まり、アプリを開くたびに予約し直します。

予約の掃除は **イベント単位** で行っています。接頭辞だけで判定すると、
グループを切り替えた瞬間に他のイベントのタイムカプセルの予約まで消えてしまい、
公開日が来ても通知が鳴らなくなります。

## 6. 動作確認チェックリスト

- [ ] 新規イベント作成 → 招待画面にQRコードが出る
- [ ] 別端末でQRコードを読み取って参加できる
- [ ] 招待コードのような、QR以外の参加手段が画面上に存在しない
- [ ] 撮影 → 約15%がタイムカプセルになる（`TimeCapsuleService.autoSelectionRate`）
- [ ] 「あとで公開」ON で撮影 → 必ずタイムカプセルになり、アルバムに出ない
- [ ] 「シェアOK」ON で撮影 → **必ず即時公開**になり、タイムカプセルには絶対にならない
      （「あとで公開」も同時ONにできない。UIで自動的にOFFへ戻る）
- [ ] タイムカプセル写真は、撮影者本人の端末でもrevealDateまでプレビューできない
      （専用タブは無く、アルバムのグリッド内にグレーの枠として並ぶだけ。中身は本人にも見えない）
- [ ] アルバムのグレーの枠には右上（または左上）に砂時計マークが付く。タップしても
      プレビューは開かない
- [ ] revealDateを迎えると、グレーの枠が自動で通常の写真セルに切り替わる
      （最大1分以内。アプリを開いたままでも切り替わる）
- [ ] グレーの枠の数は**どの参加者の端末で見ても同じ**になる
- [ ] 通知許可済みで、公開時刻に参加者全員へ通知が届く
- [ ] シェアOKの写真が**5枚**集まるごとに、イベント終了を待たずにEvent Reelが
      1件自動生成される（`ShareCollageBuilder.photosPerReel`）
- [ ] 続けて5枚集まると、既存のEvent Reelは消えずに残ったまま新しいReelが追加される
      （Event Reel #1、#2、#3…と履歴が育っていく）
- [ ] シェアOKが5枚未満の状態ではEvent Reelが**生成されない**
- [ ] Event Reel画面で過去に生成したReelがすべて一覧でき、それぞれ個別にシェアできる
- [ ] Reelに含まれる写真のシェアOKを`PhotoRepository.setShareOK(false, ...)`でOFFにすると、
      その写真を含んでいたReelの画像が**その場で作り直される**（除外された状態で）
- [ ] Reelの対象写真が0枚になった場合、そのReelは一覧から**消える**
      （`index`が飛んでも構わない。他のReelの番号は変わらない）
- [ ] OFFにした写真は、以後どのEvent Reelにも二度と使われない
- [ ] 一度何らかのReelに使われた写真は、後から `uploadedAt` が古い/新しいに関わらず
      別のReelへ移動しない（`ShareCollageStore.usedPhotoIDs`によるID単位の管理）
- [ ] `setShareOK` は `isTimeCapsule`・`revealDate` を変更しない
      （タイムカプセルの挙動に影響しない）
- [ ] 未公開のタイムカプセル写真に対して `setShareOK(true, ...)` を呼んでも
      シェアOKにならない（nilが返り、全員非公開の原則が保たれる）
- [ ] 日付をまたいでアプリを開き直しても、イベントは**自動終了しない**
      （複数日にまたがる旅行・合宿を想定）
- [ ] 手動でイベントを終了しても、タイムカプセルの枚数もEvent Reelの履歴も変わらない
- [ ] グループを切り替えて戻ってきても、タイムカプセルの枚数が変わらない
- [ ] `revealDate` を近い時刻に書き換えて検証すると、その時刻に通知が届く
- [ ] 参加者を追加してもCloudKitのEventレコードが**増えない**（重複しない）
